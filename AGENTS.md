## Start each session with environment and hook setup

Before the backlog survey or project changes, check that Pixi is
available with `command -v pixi`. If it is missing, run
`sh scripts/restore.sh` from the repository root to restore the developer
sandbox (published by `.github/workflows/pixi-sandbox.yml` from the plan
in `pixi-sandbox.toml`), then add the registered user tools to the
current shell's PATH with `export PATH="$HOME/.local/bin:$PATH"` and
verify `pixi --version`. Restore may need access to the sandbox branch
and registers user tools by default. If restore fails or Pixi remains
unavailable, report the blocker rather than claiming setup succeeded or
improvising a venv; this workspace's environment of record is
`pixi.toml` / `pixi.lock`.

Once Pixi is available, run `pixi run --locked doit install-hooks` at the
start of every session. Do not bypass a failed installation; report the
error.

## Start each session with a backlog survey

After environment and hook setup, before planning or changing the
project, survey the backlog:

```sh
pixi run backlog instructions overview
pixi run backlog milestone list --plain
pixi run backlog task list --status "In Progress" --plain
pixi run backlog task list --status "To Do" --plain
```

Read the applicable backlog specification (`backlog/docs/`) and
decisions (`backlog/decisions/`), check the workspace and Git state, and
reconcile the survey with the user's request before selecting work. Do
not let the survey override a direct user request or automatically start
unrelated work.

Use Backlog.md commands to create and update backlog records. Never edit
backlog task, decision, document, or milestone files directly, and never
mark unfinished or unverified work complete.

## Engineering rules

- The package is a **version-only scaffold** (backlog decision-4):
  `src/rude_clean_code/` contains only
  `__init__.py` and it exports only `VERSION`. Do not add rules, modules,
  or public exports without a backlog task that deliberately relaxes
  that decision.
- `VERSION` comes from installed distribution metadata built from the
  package's `pyproject.toml` (decision-2). Never hard-code a second copy
  of the version string in source.
- Keep product features and tests in the package that owns the behavior
  (decision-3): the package lives under `rude-clean-code/`
  (`{src,features,tests}`, `pyproject.toml`, `README.md`, and `LICENSE`).
  Unified repository automation tasks (`automation/dodo.py`), Gherkin
  specs (`automation/features/`), and automation BDD tests
  (`automation/tests/`) live under `automation/` (configured via root
  `doit.cfg`); pre-Pixi bootstrap and Pixi environment activation scripts
  live under root `scripts/`, with sandbox and script tests under
  `scripts/tests/`.
- For user-visible features, write a Gherkin scenario and a failing test
  in the owning package before implementation when practical.
- The environment of record is the locked Pixi workspace:
  `pixi install --locked`, then `pixi run --locked doit <task>` (or
  `pixi run --locked do <task>`; developer CLIs such as `backlog`, `skills`,
  and `agents-md` also remain direct Pixi tasks). The root `package.json` is
  the private developer-tooling manifest (the `agents-md` tool reads it);
  installing or running there only fronts the developer CLIs, it does not
  provision the product environment.
- Run all checks through `pixi run --locked doit ...`; they are the same
  commands CI runs. Report anything unimplemented or unverified.
- Commits are Conventional Commits (convco, `.versionrc`). Changelogs are
  generated from commit history; never hand-edit them.
- Documentation is part of the product: user-visible changes must update the
  canonical documents under `docs/` (see
  [docs/development/documentation.md](docs/development/documentation.md));
  run `pixi run --locked doit lint-prose` and
  `pixi run --locked doit docs-lint` before pushing.
- AGENTS.md follows the agents-md marker contract (see
  [How this file is maintained](#how-this-file-is-maintained)): the
  marked sections are owned by the `agents-md` tool; refresh them with
  `pixi run --locked agents-md` instead of hand-editing them.
- Pushes to `main` that touch the Pixi manifests republish the
  `sandbox/developer-linux-64` sandbox (`.github/workflows/pixi-sandbox.yml`).
- Do not push, create a pull request, merge, tag, publish, or release
  without explicit user authorization.

## Testing and verification

The canonical check catalogue is
[docs/guides/running-the-checks.md](docs/guides/running-the-checks.md)
and [docs/reference/pixi-tasks.md](docs/reference/pixi-tasks.md).

- `pixi run --locked doit test` — the package BDD suite
  (pytest-bdd against `rude-clean-code/features/`; steps in
  `rude-clean-code/tests/`).
- `pixi run --locked doit coverage` — the same suite with the `.coveragerc`
  gate (at least 91% total line coverage; currently 100%).
- `pixi run --locked doit test-scripts` — repository sandbox and script tests
  (`scripts/tests/`).
- `pixi run --locked doit test-automation` — repository automation BDD
  suite (`pytest-bdd` against `automation/features/`; steps in
  `automation/tests/`).
- `pixi run --locked doit` (or `pixi run --locked doit ci`) — full local CI
  check suite.
- A change is done when the full CI suite passes: `Package tests`,
  `Policy`, `Documentation`, and `Python compatibility` jobs in
  [.github/workflows/ci.yml](.github/workflows/ci.yml).

## Conventions and gotchas (durable)

- Python >= 3.11; ruff for lint and format (`ruff.toml`; isort first-party
  `rude_clean_code`); mypy (`mypy.ini`); Gherkin + pytest-bdd for product
  behavior; Conventional Commits enforced by convco in CI and the
  commit-msg hook.
- `VERSION` reads installed distribution metadata: it fails until
  `pixi run --locked doit install-projects` has run, and it goes stale
  after a `pyproject.toml` version bump until you reinstall.
- `pixi run --locked ...` requires the committed `pixi.lock`. After
  changing Pixi dependencies, regenerate the lock on a networked machine
  (`pixi lock`); conda-forge is not reachable from every authoring sandbox.
- The sandbox restore (`sh scripts/restore.sh`) materializes the conda
  environment but not the PyPI wheel cache; run `pixi install --frozen`
  online once afterwards.
- Backlog records are mutated through `pixi run --locked backlog`, never
  by hand; never mark unverified work complete.
- Vale vocabulary lives in
  `.vale/styles/config/vocabularies/Project/accept.txt` — add terms there
  instead of sprinkling exceptions through prose.
- No secrets are committed to this repository; there is no `.env`. The
  sandbox publisher authenticates with the workflow-scoped `GITHUB_TOKEN`
  (`contents: write`) and only pushes `sandbox/developer-linux-64`;
  workflows default to `permissions: contents: read`. Never commit tokens
  or keys, never widen workflow permissions, never expose `GITHUB_TOKEN`
  beyond the job that needs it.

## Boundaries (durable)

- ✅ **Always**: run `pixi run --locked doit test` before committing; keep
  product code and tests inside the owning package (`rude-clean-code/src/`,
  `rude-clean-code/features/`, `rude-clean-code/tests/`); keep docs in
  sync with behavior (the documentation standard applies); write
  Conventional Commits.
- ⚠️ **Ask first**: relaxing the version-only scaffold (decision-4);
  adding public exports or distributions; touching
  `.github/workflows/` or the sandbox publisher; adding or removing
  dependencies; anything affecting release, tag, or publish.
- 🚫 **Never**: commit secrets or API keys; push, merge, tag, publish, or
  release without explicit user authorization; edit `backlog/` records or
  `.agents/` skills by hand; hand-edit `pixi.lock` or `bun.lock`; edit
  generated or build output; force-push `main`; bypass hooks with
  `--no-verify`.

## How this file is maintained

The marked sections above are owned by
[agents-md](https://github.com/eugeniughelbur/agents-md)
(`@eugeniughelbur/agents-md`, installed as a developer dependency and
pinned in `bun.lock`). The durable sections below explain the contract —
read them before running the tool:

- Content **inside** `<!-- agents-md:begin id=... -->` /
  `<!-- agents-md:end id=... -->` markers is regenerated from repository
  metadata (package.json `description` and `scripts`, top-level layout,
  git state) by `pixi run --locked agents-md`. The tool never fabricates:
  what it cannot detect becomes a `_TBD: ..._` stub, and re-runs rewrite
  the sections from the current metadata.
- Content **outside** the markers — the start-of-session sections, the
  engineering rules, the testing, conventions, and boundaries sections
  above, and this section — is human-owned and is never touched by
  re-runs. Durable operational truth belongs there.
- The marked sections are therefore intentionally minimal. The durable
  equivalents: the [Boundaries (durable)](#boundaries-durable) section
  overrides the marked boundaries stub; [Testing and
  verification](#testing-and-verification) and [Conventions and gotchas
  (durable)](#conventions-and-gotchas-durable) override the matching
  marked stubs. The canonical detail lives in `docs/`
  ([docs/README.md](docs/README.md)).
- The `npm run <script>` commands in the marked Commands section front
  the same doit tasks listed in
  [docs/reference/pixi-tasks.md](docs/reference/pixi-tasks.md) (see the
  `package.json` scripts); `pixi run --locked doit ...` remains the
  invocation of record.
- If you change commands, layout, or conventions, update both the
  human-owned sections and whatever the tool reads from metadata, then run
  `pixi run --locked agents-md` and review the diff. A re-run is a safe
  refresh, not a reset — it cannot touch human-owned content.
- A hand-written `AGENTS.md` without markers is never overwritten by the
  tool (it writes `AGENTS.generated.md` beside it instead) — that is why
  this file keeps its markers after curation.
- `CLAUDE.md` is a symlink to this file so Claude Code reads the same
  guidance; do not replace it with a divergent copy.
- markdownlint is relaxed (MD022, MD032, MD034, MD036) only around the marked
  sections via inline `markdownlint-disable` comments, because the
  tool's compact rendering would otherwise fail `docs-lint` after every
  re-run; the rules stay enabled for the human-owned sections.
